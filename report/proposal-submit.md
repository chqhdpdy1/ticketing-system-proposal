## 2. 프로젝트 주제

**주제명:** Ticketing System — 여러 분야에 두루 쓸 수 있는 선착순 판매 시스템 (첫 적용 분야: 영화관 티켓 예매)

**설명:** 수량이 한정된 상품을 짧은 시간에 많은 사람이 동시에 사려고 몰리는
"선착순 판매" 상황을 문제 없이 처리하는 시스템을 만든다. 영화 좌석, 공연 좌석,
한정판 상품처럼 파는 대상이 달라도, 선착순 판매에는 다음과 같은 공통 어려움이 있다.

- **동시에 몰림:** 같은 좌석·상품을 여러 명이 동시에 사려고 한다.
- **순간 폭주:** 판매가 열리는 순간 접속이 갑자기 몰린다.
- **순서 지키기:** 먼저 온 사람이 먼저 살 수 있어야 한다.
- **재고 정확성:** 결제가 실패하면 잡아둔 자리를 다시 풀어줘야 한다.

이 공통 문제를 해결하는 **공용 판매 엔진**을 먼저 만들고, 그 위에 **영화관 티켓 예매**를
첫 번째로 올린다. 결제·문자 발송 같은 외부 기능은 실제로 연결하지 않고 **가짜(테스트용)**
로 대신한다.

## 4. 시스템 목표 (Vision & Scope)

**목표(Vision):** 여러 판매 분야에 그대로 재사용할 수 있는 선착순 판매 엔진을 만든다.
이 엔진은 (1) 재고보다 많이 파는 실수가 없고(**정확**), (2) 사람이 몰려도 멈추지 않으며
(**안정**), (3) 먼저 온 사람이 먼저 사는(**공정**) 것을 목표로 한다.

**범위(Scope):**

- **이번에 만드는 것:** 선착순 판매 엔진(판매·재고·자리잡기·주문), 동시 접속 처리,
  영화관 기능(상영·좌석·예매·티켓 발급), 간단한 로그인, 가짜 결제·알림.
- **만들지 않는 것:** 실제 카드 결제·문자 발송, 추천·정산 같은 부가 기능, 스마트폰 전용 앱.

**As-Is / To-Be (기존 방식 → 이번 프로젝트):**

| 구분 | As-Is (기존 방식) | To-Be (이번 프로젝트) |
|------|-------------------|------------------------|
| 구조 | 판매 분야마다 판매 기능을 매번 새로 만듦 | 공용 엔진을 만들어 여러 분야에 재사용 |
| 동시 접속 | 재고 확인과 차감이 따로 놀아 초과 판매 발생 | 확인·차감을 한 번에 처리해 초과 판매 없음 |
| 순간 폭주 | 판매 시작 순간 서버가 느려지거나 멈춤 | 대기줄을 두어 한꺼번에 몰리지 않게 함 |
| 재고 정확성 | 결제 실패 시 자리가 묶인 채 낭비됨 | 일정 시간 뒤 자동으로 자리를 다시 풀어줌 |

## 5. 시스템 개요 및 특성

**주요 특징:**

- 기능을 **화면 / 판매 엔진 / 저장소** 등 역할별로 나누어, 서로 영향을 덜 주게 만든다.
- 재고를 줄일 때 **확인과 차감을 한 번에** 처리해, 재고보다 많이 파는 일을 막는다.
- 판매가 열리면 **대기줄**을 두어 접속이 한꺼번에 몰리지 않게 조절한다.
- 자리를 잡아두면 **일정 시간(예: 5분)**만 유지되고, 결제하지 않으면 자동으로 풀린다.
- 결제·알림은 실제 연결 대신 **가짜 기능**으로 바꿔 끼울 수 있게 만든다.

**주요 기능(Use Case)별 요구사항:**

> 아래 표의 "설계 원칙" 항목은 과목에서 배우는 구조 개념(구조 스타일 / GRASP / SOLID / 디자인 패턴)을 적용 예시로 표기한 것이다.

| 기능 | 하는 일 | 다루는 정보 | 필요한 기능(FR) | 적용 설계 원칙 | 품질 목표(NFR) |
|---|---|---|---|---|---|
| 판매 목록 보기 | 상영(판매) 목록·상세를 보여줌 | 상영 정보, 남은 수량 | 목록·상세 조회, 오픈까지 남은 시간 표시 | Layered / Information Expert / Repository | 빠른 응답 |
| 대기줄 입장 | 몰린 사람을 순서대로 입장시킴 | 사용자, 순번, 입장권 | 대기표 주기, 순번 알려주기, 순서대로 입장 | 큐 / Controller / Strategy | 공정함, 안정성 |
| 자리 잡기 | 좌석을 잠시 맡아둠 | 좌석, 사용자, 유지 시간 | 재고를 정확히 하나만 줄이기, 중복 잡기 막기 | Ports&Adapters / Low Coupling / State | 정확함, 동시 처리 |
| 주문·결제 | 맡은 자리를 실제 구매로 확정(가짜 결제) | 주문, 금액, 결제 | 결제 요청, 성공 시 확정·실패 시 자리 풀기 | Facade / Adapter / Template Method | 믿을 수 있음 |
| 티켓 발급 | 구매 후 티켓을 발급·조회 | 티켓, 좌석, 상영 | 티켓 번호 발급, 예매 내역 보기 | Factory Method / Creator | 관리 쉬움 |
| 판매 등록 | 관리자가 상영·좌석·수량 등록 | 상영, 좌석, 가격 | 상영·가격·오픈 시각 등록, 재고 설정 | Layered / Builder | 보안(권한) |
| 취소·환불 | 예매를 취소(가짜 환불) | 주문·티켓 상태 | 취소하기, 자리 되돌리기, 환불(가짜) | Command / Observer | 정확함 |

**추가 품질 목표(NFR):**

| 품질 목표 | 바라는 모습 | 이루는 방법 |
|---|---|---|
| 정확함 | 아무리 몰려도 재고보다 많이 팔지 않음 | 확인·차감을 한 번에 처리, 중복 방지 규칙 |
| 안정성 | 판매 시작 순간에도 멈추지 않음 | 대기줄로 접속 조절, 응답 지연 방지 |
| 빠른 응답 | 조회·자리잡기가 빠름 | 자주 쓰는 정보 미리 저장(캐시) |
| 확장 용이 | 서버를 늘리면 처리량도 늘어남 | 서버가 상태를 안 들고 있게 설계 |
| 공정함 | 먼저 온 사람이 먼저 삼 | 대기줄 순번 관리 |
| 재고 정확성 | 결제 실패 시 자리를 되돌림 | 시간 지나면 자동 반환 |
| 관리 쉬움 | 새 판매 분야를 쉽게 추가 | 공용 엔진은 그대로 두고 기능만 끼움 |
| 보안 | 로그인·권한 구분, 중복 요청 막기 | 로그인 토큰, 중복 요청 차단 |

## 6. 사용 기술 및 Framework

대규모 선착순 판매를 하는 예매 사이트(인터파크, Ticketmaster 등)와 한정판 판매
서비스들은 공통적으로 **대기줄, 빠른 재고 관리, 작업을 나눠 처리하기** 방식을 쓴다.
본 프로젝트도 이 방식을 참고해 아래 기술로 만든다.

| 구분 | 사용 기술 | 선택 이유 |
|------|-----------|-----------|
| 개발 언어·틀 | Java 17 + Spring Boot 3 | 자료가 많고 배우기 좋음 |
| 데이터 저장 | PostgreSQL (관계형 DB) | 데이터를 정확하게 지켜줌 |
| 빠른 저장소·대기줄 | Redis | 재고 처리와 대기줄에 적합 |
| 통신 방식 | REST API | 표준적이고 다루기 쉬움 |
| 화면(프론트) | React (간단한 화면) | 예매 흐름을 보여주기 위함 |
| 테스트·부하 시험 | JUnit5, k6 | 동시 접속 상황을 시험 |
| 실행 환경 | Docker | 어디서나 똑같이 실행 |

**참고해서 가져올 부분:** 예매 사이트의 "대기줄" 개념을 대기줄 기능으로, 빠른 재고
관리 방식을 Redis를 이용한 재고 처리로 구현한다.
