# Architecture Decision Records — v2.0

상태: 설계 채택, 구현·실측 검증 전. 날짜: 2026-10-31.

## ADR-001 PostgreSQL을 거래 진실원본으로 선택

- 문제: Redis 선차감·DB 후행 기록 사이의 장애 구간을 DB Outbox만으로 원자화할 수 없다.
- 선택: StockUnit·Hold·Order·Payment·Ticket을 DB에서 일관되게 변경.
- 대안: Redis 재고+내구 이벤트 로그+재조정. 복구·운영 부담으로 보류.
- 비용: DB 잠금 경합·처리량 한계. 대기열과 측정으로 대응.

## ADR-002 모듈러 모놀리스

- 선택: 단일 Spring Boot 배포, 패키지·포트로 경계 유지.
- 이유: 1인 팀에서 분산 장애·배포 복잡도보다 거래 정확성 검증 우선.
- 재검토: 실측 병목과 독립 배포 필요가 확인될 때.

## ADR-003 지정 단위·한 주문 한 좌석

- 선택: StockUnit 하나는 판매 가능한 개별 단위. v2는 Hold/Order 당 좌석 하나.
- 비용: 다좌석·SKU 수량은 지원하지 않음.
- 재검토: HoldGroup/OrderLine·수량 재고 모델과 잠금 순서를 설계한 후 확장.

## ADR-004 Mock 결제와 동기 발권

- 선택: 외부 효과 없는 결정적 Mock을 거래 안에서 계산. PAID/SOLD/Ticket 함께 커밋.
- 비용: 실제 PG를 단순 어댑터 교체만으로 지원하지 않음.
- 재검토: 실제 PG 도입 시 payment attempt·UNKNOWN·provider idempotency·조회·환불 보상 도입.

## ADR-005 DB 기반 만료

- 선택: expires_at·잠금 후 DB 시각·조건부 상태 전이·재시도 스케줄러.
- 이유: TTL 이벤트 유실·중복·결제 경합에 재고 원장을 의존시키지 않음.
- 비용: 만료시각과 재판매 가능 시각 사이의 짧은 지연. 정상 상태 5초 이내 목표를 측정.

## ADR-006 제한된 선착순

- 선택: Redis가 원자적으로 접수한 순번에 따라 입장 권한 부여. 입장 이후 구매 경쟁은 별도.
- 비용: 엄격한 구매 완료 FIFO나 Redis 데이터 유실 전후의 순서 복원은 제공하지 않음.

## ADR-007 Outbox 적용 범위

- 선택: 알림에만 사용, 거래 핵심 변경은 동기 처리.
- 이유: 초기 단계에서 발권 누락·재고 복원 지연의 비동기 실패 구간 축소.
- 비용: 거래 경로의 DB 쓰기 증가. 전달은 at-least-once, exactly-once 외부 효과는 보장하지 않음.

## ADR-008 결제 후 취소·환불 보류

- 선택: 미결제 선점 해제만 지원. PAID 주문 취소 API는 v2에 없음.
- 이유: 환불 승인·티켓 무효화·좌석 재판매의 추가 불변식이 필요.
- 재검토: 환불 상태 머신과 재판매 이력을 설계한 후 별도 유스케이스로 도입.
